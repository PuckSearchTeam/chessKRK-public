# Running Puck on the engine and on the naive engine

Two constraint files, written in Weland as the paper defines it (Section 4.2). The context comes first:
`axis name = [ … ]` declares an axis of change and its tagging; `speed a < b < c, d;` the speed of change,
slowest first (`a < b` reads "a changes less often than b"); `difficulty X < Y;` the difficulty to change (`Y`
is harder than `X`); and `apart a, b, c;` the decision to keep unordered axes apart. The clauses follow from
them: `speed a < b` generates `hide b from a`, the faster hidden from the slower; `difficulty X < Y` generates
`hide X from Y`, the easier hidden from the harder; both along the transitive closure of the chains; `apart`
hides each axis of its group from the others. The written clauses remain: `hide X except X' from Y
but-not-from Y';`, bare `hide X;`, `separate X;` and `friend F of X;`, and `set name = [ … ]` for a set that
is not an axis. Where a clause takes a set it may list several, `hide strategies from rules, policy;`, their
union being meant; an axis may be declared empty, `axis policy = []`, an axis of the context that has no
entity yet. Names are the fully qualified names Puck gives to nodes: packages, types, `Class.field`,
`Class.method(ParamType,…)`; a method's parameter list is part of its name, so commas inside parentheses need
no quoting. Line comments start with `//`. The set `tests` is predefined: the classes, and their members,
under the project's test source roots. A file written before the context syntax, with `set` and `hide`
clauses only, still works: every set but `tests` is then an axis.

| File | Project directory | Sets |
|---|---|---|
| `decouple.wld` (repository root) | the repository root | the seven axes of the paper, §5.1–5.2, one package or two each |
| `Before/decouple.wld` | `Before/` | the same seven axes on the naive engine, §5.5: a package tagged `rules`, classes and members tagged with their own axis, `policy` and `pieces` empty |
| `After/decouple.wld` | `After/` | the same seven axes on the refactored naive engine (the initial commit, same functionality as `Before/`): `valuation` is the tablebase alone, `pieces` is empty |

**The part of the two files after the axes is identical**; only the axis lists differ. It has three parts: the
speed chain, from which Puck generates the six clauses of the Dependency Rule, two decisions of the architect
(`friend wiring of all;`, `friend tests of all;`), and an **optional block** between `// BEGIN optional` and
`// END optional`, one `apart` statement over the four unordered axes, which makes the permitted relation
between axes acyclic and brings ADP in (paper, Proposition 1). Puck reads `decouple.wld` at the project's base path and collects every
`.java` file below it, tests included. The kept results of the runs of 2026-10-06 are in `docs/puck-results/`
(`puck-with-optional.log`, `puck-without-optional.log` and the violation-only `.dot` graphs of each run, with the
constraint file they were produced from).

Each violation line of the log ends with the repair that removes it, the row of Table 3 of the paper chosen from
the kind of edge and from what generated the clause: a containment edge (`--c-->`, a foreign entity in a
container of another axis) gets `[SRP, CCP: Move Method or Move Class into a container of the entity's axis, or
Extract Class]`; a use edge (`--u-->`) against a clause generated by `speed` gets `[OCP, DIP: Extract Interface
into the user's axis and redirect the use; Introduce Parameter or a factory for an instantiation]`, against one
generated by `difficulty` `[SDP: the same inversion, or move the dependency to an entity that is cheaper to
change]`, against an `apart` statement `[OCP, DIP, between axes kept apart: Extract Interface into the user's axis and redirect
the use]`, and against a written clause `[written clause, a decision of the architect (ADP when it directs an unordered
pair): the same inversion, or revise the decision]` (since 2026-10-20; before, every written clause was labelled ADP,
which was wrong for the 525 GUI violations of ArgoUML). The inspection message in the editor ends with the same repair. The tool names the refactoring; it
does not perform it.

## How to run

### Headless, from the command line

The plugin has a command-line entry point, `puck`, that opens each directory given as a project, waits for
indexing, runs the same check as **Tools → Puck** and prints `puck.log`. From `Puck/`:

```bash
./gradlew runIde "-PideArgs=puck;--jdk=C:/Program Files/Java/jdk-21;--both;D:/repos/chessKRK/Before;D:/repos/chessKRK/After"
```

`scripts/puck-both.sh <project dir>...` is the usual way to run it: one IDE launch for all the directories given,
each checked twice, with the file as written and with its optional block commented out, both logs kept next to
the file (`puck-with-optional.log`, `puck-without-optional.log`; `puck.log` is the former). The JDK comes from
`PUCK_JDK`, then `JAVA_HOME`. The IDE start is paid once per launch, so give the script every subject at once.

- `ideArgs` is the IDE's command line, `;`-separated: the command, then options and project directories.
  `--jdk=` names a JDK registered in the sandbox or the path of a JDK home (a JDK is needed for the project to be
  configured; the check itself only resolves references between the project's own sources). `--both` does the
  two runs described above. The original form `puck;<dir>;<jdk>` still works.
- When a directory has no `.idea` folder, the command writes one first, plus a `<name>.iml` with one module
  whose content root is the directory and whose source roots are `src/main/java` and `src/test/java` when they
  exist, exactly as if the directory had been opened in the IDE and configured by hand. No Maven or Gradle
  import is performed. Both files are ignored by git here. The test source root is what defines the predefined
  set `tests`.
- **Excluded directories** are left out, of the module and of the analysis: build outputs and tool directories
  (`target`, `build`, `out`, `.git`, `.gradle`, `.idea`, `idea-sandbox`, `.intellijPlatform`, `node_modules`) and
  nested projects, a directory holding its own `decouple.wld`, `pom.xml`, Gradle build file or `.idea`. So the
  run on the repository root checks the engine alone: `Before/`, `After/`, `Puck/`, `Oracles/` and the examples
  are projects of their own. (Before 2026-10-12 it collected every `.java` file below the root, which merged
  `After/`, whose packages are the engine's, into the engine's graph.)
- The build targets a local IntelliJ installation given by the Gradle property `puck.ide` (for instance in
  `~/.gradle/gradle.properties`: `puck.ide=C:/Program Files/JetBrains/IntelliJ IDEA Community Edition 2025.1.4.1`);
  without it an IntelliJ IDEA Community distribution is downloaded. Gradle 9 is required; the JDK 21 the build
  needs is downloaded when none is installed.
- Exit code 0: every check ran; 2: a directory could not be opened; 3: a `decouple.wld` has errors (listed in
  `decouple.err`).

### In the IDE

Open the directory as a project, then **Tools → Puck**. The results are also shown as warnings by the *Puck
Inspection*; since the batch-mode change, **Code → Inspect Code** runs the check by itself when the action has not
been run yet.

### Outputs

Written next to `decouple.wld`: `puck.log` (every violated edge, grouped by rule, with counts), `graph.json`
(nodes with positions, edges, rules, violations), `graph.dot` (the whole graph with violations in red), one
`<rule>.dot` and one `<rule>_RedOnly.dot` per rule (`containment_between_axes.dot` for the axis-mismatch check), a `cytoscapejs/` viewer with `start_server.*` scripts, and
`decouple.err`. All of them are ignored by git except the copies kept in `docs/puck-results/`.

In `puck.log`, `--u-->` is a use edge and `--c-->` a containment edge; `A --u--> B` reads "A uses B" and the rule
is violated because B is hidden from A.

## Semantics implemented by the plugin

With X↓ the **effective closure** of a set reference (paper, Section 4.3): the named entities and everything
they contain, minus the scopes of the entities that a set outside the reference names inside them, which are
foreign entities and belong to that other set with their own scope. A reference naming several sets is the union of their
closures. In the naive engine this gives `rules` the package, `Engine` and its 21 rule members (23 entities),
`protocol` `Main`, `main`, `send` and the seven foreign members of `Engine` (10), `valuation` 13, `strategies`
3, `wiring` 2, `policy` and `pieces` 0, as the paper's tagging says.

- `hide X except X' from Y but-not-from Y';`: no element of Y↓ \ Y'↓ \ X↓ may use an element of X↓ \ X'↓. The
  subtraction of X↓ ("we don't hide from ourselves") is the paper's formula; `from` absent means every node of
  the graph. A clause on an empty set holds vacuously.
- `separate X;`: for each element named by X, its effective closure is hidden from those of the other
  elements; the checker generates one rule per element, reported as `separate X; (z)`.
- `friend F of X;`: a use by an element of F↓ of an element of X↓ is never a violation, whatever the rule;
  `of all` exempts every use by F↓.
- `tests` is predefined as the nodes declared under a test source root (packages, shared with production code,
  are never in it); a `set tests = [...]` in the file overrides it. `friend tests of all;` thus leaves the tests
  out of the rules: they assemble concrete variants of every axis, for their own reason and from every package,
  and are neither *wiring* nor an axis.
- **Containment between axes** (paper, Clause 3 and Proposition 1): the axes are those declared with `axis`
  (every set but `tests` in a file without any), and every node gets the axis whose effective closure holds it. Puck then reports every containment edge whose
  two ends have different axes, one per axis mismatch (a foreign entity in its container). A hide clause reports the mismatches against the order, the hidden
  axis declared inside the hiding one, and keeps them; the rule `containment between axes` reports the others,
  the mismatches in the direction the orders permit, which no hide clause can see (a *rules* method declared in a
  *protocol* class, say). The log ends the rule with `Axis mismatches: n (k reported above by hide clauses, m here)`. A
  node named by two sets has no axis; `friend` exemptions apply.
- Package nodes exist only for packages with a package statement (none for `application.port`, hence the `policy`
  set names `port.in` and `port.out`).
- Javadoc `{@link}` references are resolved and counted as uses.

The grammar is in `Puck/src/main/java/fr/lip6/move/puck/parse/weland.bnf`; the parser is hand-written from it
and the lexer generated with JFlex (`jflex-1.9.1.jar` and `idea-flex.skeleton` in `Puck/`).

## Results (2026-10-06, rerun on 2026-10-13)

Every subject was rerun on 2026-10-13 with its constraint file rewritten in the context syntax (`axis`, `speed`,
`difficulty`, `apart`), buckpal and library included, cloned again at the cited commits. The generated clauses
reproduced every count below, edge for edge, and the kept logs are those runs: they list the generated clauses
first, then the written ones, and end with the `containment between axes` rule and the `Axis mismatches:` line (every
mismatch reported by a hide clause, none by the new rule). The one visible difference from the 2026-10-06 logs is
the clause on wiring, `hide wiring from` the six other axes, generated by the chain, where the files used to
write `hide wiring;`. The kept copies are refreshed with `scripts/puck-both.sh`, all subjects in one launch.

### Clean engine (`decouple.wld` at the root)

53 Java files (the engine's sources and tests, plus `scripts/Equivalence.java`) and 469 nodes, 114 of them under
the test source root; the nested projects under the root are left out since 2026-10-12 (before that the run
collected 117 files, `Before/`, `Examples/` and `Puck/` included, which added nodes but no violation; the
addition of `After/`, whose packages are the engine's, then showed why nested projects must be excluded). **Puck
reports no violation, with or without the optional block**: the file holds on the whole project, tests included.

For the record, without `friend tests of all;` the same file reports **0** edges too (rerun 2026-10-20, kept as
`docs/puck-results/engine/puck-without-friend-tests-{with,without}-optional.log`): since the context syntax of
2026-10-13 the test classes, named by the predefined set `tests`, are foreign to every axis (`removeForeignScopes` in
`PuckAction.Closures`), so no generated clause covers them; the friend clause only extends the exemption to a bare
`hide X;`, which hides from every node. The tests' 735 uses of production code are in the graph (`graph.json`). The
118 edges of 2026-10-06 were measured under the earlier file, whose bare `hide X;` clauses hid from every node.

### Refactored naive engine (`After/decouple.wld`)

21 Java files, 48 nodes under the test source root. **Puck reports no violation, with or without the optional
block.** This is the end state of the identify-then-fix experiment: the same functionality as `Before/`, checked by
`scripts/Equivalence.java` (every answer of both engines legal and mate-optimal on all 175,168 positions), with the
architecture of the root engine before any feature was added.

### The engine before and after the piece catalogue redesign (§5.4)

Two snapshots of the git history, extracted with `git archive <commit> src pom.xml` into a scratch directory
and checked with `scripts/puck-both.sh <dir>`; their files and logs are kept in `docs/puck-results/pieces-before`
and `pieces-after`.

- **Before** (`79a367d`, the concrete pieces are the constants of the `PieceType` enum in `domain`): the root
  file with `pieces` listing the five constants, plus `separate pieces;`. Under the Dependency Rule alone,
  **10 edges**: the five containment edges `PieceType --c--> KING … KNIGHT` (the foreign entities, SRP by Proposition 1)
  and five uses by *rules* (`Piece.isKing`, `Piece.WHITE_KING`, `Piece.BLACK_KING` → `KING`;
  `Material.isDead` → `BISHOP`, `KNIGHT`). With the optional block, **12**: the two uses in
  `MatingNetHeuristic.smallestBox` → `ROOK`, `QUEEN` (*valuation* and *pieces* are unordered). `separate pieces;`
  reports nothing: no constant names another (`puck-without-separate.log`).
- **After** (`9eb6659`, `PieceType` an interface with a `PieceCatalog` in `domain`, the pieces data of
  `StandardPieces` in `adapter.pieces`): the root file as is. **0 edges**, with or without the optional block.

### Programs the authors did not write (§5.6)

Context declared from the README and the package layout, results in `docs/puck-results/buckpal` and `library`

- **buckpal** (thombergs/buckpal `dc819c6`, 31 classes, the example of "Get Your Hands Dirty on Clean Architecture"):
  model ≻ ports ≻ commons ≻ services ≻ {web, persistence} ≻ wiring (the services below the adapters since 2026-10-20, as the engine's strategies), `separate ports;` for the author's own rule. **1 edge**

### Naive engine (`Before/decouple.wld`)

4 Java files, 56 nodes, 5 of them under the test source root.

**Without the optional block, the Dependency Rule alone: 26 violated edges** (since 2026-10-19, the strategies ranked
below the adapters; rerun on 2026-10-20; findings numbered as in §5.5 and `Before/VIOLATIONS.md`):

| Rule | Edges |
|---|---|
| `hide strategies from rules, policy;` | `Engine` contains `bestMove()`, `tablebase()`, field `tablebase` (3 foreign members, finding 1) |
| `hide valuation from rules, policy, strategies;` | the package contains `Tablebase` (1 foreign class, finding 2); finding 3, the strategy using the tablebase: `Engine.tablebase() → Tablebase`, `→ Tablebase.Tablebase()`; `Engine.bestMove() → Tablebase`, `→ Tablebase.plies(int,int,int,boolean)`; field `Engine.tablebase → Tablebase`; `Engine → Tablebase`, the javadoc `{@link}` in the class comment (6 edges) |
| `hide protocol from rules, policy, strategies;` | the package contains `Main` (1 foreign class, finding 2); `Engine` contains `setPosition`, `clear`, `parseFen`, `parseSquare`, `squareName`, `moveName`, `valid` (7 foreign members, finding 1); finding 4, the strategy using the protocol: `Engine.bestMove() → Engine.valid`, `→ Engine.moveName(int)`, `→ Main`, `→ Main.send(String)` (4 edges) |
| `hide wiring;` | `Main` contains `OUT`, `ENGINE` (2 foreign fields, finding 1); `Main.main → Main.ENGINE`, `Main.send → Main.OUT` (finding 5) |

That is the fourteen axis mismatches (findings 1 and 2, decided on the context) and twelve uses (findings 3, 4 and 5).
The clauses on `policy` and `pieces` hold vacuously.

**With the optional block: 29 violated edges**: the three of finding 6, `Tablebase` (valuation) using `Main.send`
(protocol), two unordered axes: `Tablebase.Tablebase() → Main`, `→ Main.send(String)`; `Tablebase → Main` (javadoc
`{@link}`). Before the re-ranking the block also reported `Main.main` using the strategy (2 edges) and findings 3 and 4
(then between unordered axes), 31 in all; those are now reported by the order (3, 4) or permitted (an adapter using a use
case).

Finding 7 (the cycle strategies → valuation → protocol → strategies) is not an edge; it is read off findings 3, 6 and the
permitted use of the strategy by `Main.main`, by Proposition 1, which the optional block is what makes applicable.

So the Dependency Rule alone finds the cohesion defects (through the context), the strategy's uses of the tablebase and
of the protocol, and the dependency on the composition; the tablebase printing through `Main` and the cycle are found
only when the architect asks for ADP.
